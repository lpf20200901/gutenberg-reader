# 静默失败：四个不报错的 bug

这个项目里所有难缠的问题都有同一个特征：**它们不报错。**

没有异常，没有警告，测试是绿的，程序正常退出。你得到的是一个看起来完成的产物，
而它是坏的。这类 bug 比崩溃危险得多——崩溃告诉你出事了，静默失败告诉你一切正常。

下面四个案例，每个都是真实发生的，附排查过程和根因。

---

## 案例一：发出了一本只剩 25% 的书

### 现象

下载六本电子书，全部显示成功。

### 排查

唯一的不对劲是**文件大小**。我顺手拿落盘大小去比 HTTP 响应头里声明的 `Content-Length`：

| 书 | 应有 | 实收 | |
| --- | --- | --- | --- |
| 警世通言 | 1,176,833 | 1,176,833 | ok |
| 喻世明言 | 1,130,409 | 1,119,627 | 残 |
| 醒世恒言 | 1,651,633 | 1,168,587 | 残（71%） |
| 初刻拍案惊奇 | 1,213,458 | 1,091,067 | 残 |
| 二刻拍案惊奇 | 968,635 | 813,628 | 残 |
| **今古奇观** | **2,896,630** | **724,887** | **残（25%）** |

六分之四被截断，最严重的一本只剩四分之一。

### 根因

```python
with urlopen(url) as r, open(dest, "wb") as f:
    while chunk := r.read(65536):
        f.write(chunk)
```

这段代码**逻辑上没错**——问题在于它假设"`read()` 返回空"只有一种含义：文件读完了。

但实际上有两种：

1. 文件正常读完 → `read()` 返回 `b""`
2. **连接被中断** → `read()` 也返回 `b""`

循环无法区分这两者，于是把"下载失败"当成了"下载完成"。

### 修法

加一道**完整性闸门**：字节数必须等于 `Content-Length`，否则抛异常、拒绝发布成品文件。

同时加 `Range` 续传。这不是理论收益——修复后实测：

| 书 | 失败次数 | 断点位置 |
| --- | --- | --- |
| 今古奇观 | 3 | 17%、37%、**99.6%** |
| 醒世恒言 | 2 | 62.8%、**99.0%** |

注意有几次断在 **99.0% 和 99.6%**——差最后几 KB。没有续传的话，每次都要从零重下。

### 教训

**别信"操作成功"，要信"结果符合预期"。** 文件写完了不等于内容完整；
`Content-Length` 是服务端给的独立见证，用它交叉验证。

## 案例二：一个 API 得了 98 分

### 现象

繁体转简体。Windows 上有现成 API：`LCMapStringW` + `LCMAP_SIMPLIFIED_CHINESE`。

我拿 100 个高频繁体字测了一遍：**98/100**。看起来是个能用的方案。

### 排查

转完之后我**随手看了一眼输出**，发现读起来不对劲：

```
TRAD: 公既騎，乃别而去……果有張生於是日死矣。後九年，母
SIMP: 公既骑，乃别而去……果有张生於是日死矣。後九年，母
                                        ↑ 没转   ↑ 没转
```

`張→张`、`時→时`、`問→问` 都转了，但 `於` 和 `後` 漏了。**于是结果是一份繁简混杂的文本**
——比纯繁体更难读，因为读者会在简体里不停撞到繁体字。

我是拿一张 480 对的参照表去逐个探测这个 API，才看清缺口有多大：

| 漏字 | 应为 | 出现次数 |
| --- | --- | --- |
| `爲` | 为 | **2,052** |
| `於` | 于 | **1,701** |
| `後` | 后 | 798 |
| `蹟` | 迹 | 96 |
| `衆` | 众 | 62 |
| …… | | 共 11 字 **4,800 处** |

最讽刺的一处：这个 API **能**正确转换 `為 → 为`（464 处），却完全不管它的异体字 `爲`
（2,052 处）。

### 根因

这是操作系统的映射表，不是完整的转换器。它有缺口，而且**遇到缺口时不做任何表示**——
不抛异常、不返回错误码、不记录日志，就是把那个字原样留在那儿。

98% 的准确率听起来很高，但在这个场景里，**2% 的失败率意味着每 50 个字里就有 1 个是错的**，
而且错得毫无规律。

### 修法

在 API 之后补一张 11 条的表。更重要的是一套**校准方法**：

```python
def audit_gaps(text, reference_pairs):
    """拿参照表探测引擎，返回它在这个文本里漏掉的字，按出现频率排序。"""
```

**为什么要按文本校准**：补丁量取决于文本用了哪些字，不是固定开销。实测：

| 书 | 引擎转换 | 需补丁修补 |
| --- | --- | --- |
| 今古奇观 | 211,469 | 4,217 |
| 聊斋志异 | 98,899 | 4,811 |
| 喻世明言 | 73,693 | **3** |

喻世明言只需补 3 个字。换一本书，缺口清单就得重算。

### 教训

**覆盖率不是正确率。** 98% 的覆盖率配 0% 的报错率，等于一份坏掉的成果加上一份完好的假象。
测量覆盖率的时候，必须同时问："剩下那 2% 是什么？会不会被静默吞掉？"

## 案例三：40 卷塌成 42 段

### 现象

生成阅读页，标题全对——40 卷、40 篇，一个不少。**但段落只有 42 个。**

一本 40 万字的书，平均每段将近一万字。也就是**整章被合并成了一段**。

### 排查

没有任何报错。线索是那个段数——40 卷的书出现 42 段，这个数字太可疑（40 + 2）。

于是我把源文件的**行首字符**打出来看（用 `repr()`，否则看不见）：

```
'　　這首詞名為《西匯月》，是動人安分守己…'   ← 2 个全角空格
'色、財、气四宇，損卻精神，虧了行止…'        ← 什么都没有
```

**段首缩进、续行不缩进**——中文排版的通行惯例，这就是分段信号。

再统计一下整个文件：

```
醒世恒言    缩进行 3,250 个     空行只有 118 个
```

**空行根本不够用。** 我原来的实现靠空行分段，而这本书平均 27 个段落才摊到 1 个空行。

### 根因

我最初的解析代码是这样的：

```python
for line in text.splitlines():
    line = line.strip()          # ← 就是这一行
    ...
```

`strip()` 把行首的缩进**连同分段信号一起扔掉了**。之后无论怎么判断，都再也分不出
"新段落"和"续行"。信息在第一步就没了，后面补不回来。

### 修法

保留行首空白，用缩进判定段落边界。同时要把"续行"重新接回去——
不然一本书会被切成每 30 字一块。

顺便发现这类书的排版还有第四种：有的转写**每行 28 字、每行后面还插一个空行**，
全文 10,334 个空行。按空行切会把一个段落切成十几块（实测 `blocks=10,317`），
所以还得加一个"硬换行"模式。

三档自动判定：

```
indent  ← 缩进行数 ≥ 50 且 缩进行数 > 空行数 + 50
unwrap  ← 中位行长 ≤ 45 且 无句末标点的行占比 ≥ 0.35
blank   ← 其余
```

### 教训

**别在判断之前做无谓的规范化。** `strip()` 看起来是无害的清理，实际是**有损操作**。
处理格式不规范的输入时，先问一句："我要扔掉的这个空白，会不会正是我在找的信号？"

顺便：**"标题全对"会让人放松警惕。** 结构识别对了，不代表内容没坏。
我是靠"段落密度"这个指标发现异常的——健康区间是每段 100–400 字，
一万字一段明显不对。给输出定几个可量化的健康指标，比肉眼看更有用。

## 案例四：测试抓到的一个我根本没想到的失败模式

前三个案例都是我"看"出来的。这一个不同——**是测试抓出来的，不是我看出来的。**

### 现象

我给繁简补丁表写了参数化测试：每个补丁条目都应该生效。

```
FAIL: test_every_patch_entry_converts (trad='鍾')
AssertionError: '钟' not found in 'x锺y'
```

5 个失败。

### 排查

重点是错误信息里的 `'x锺y'`——**输入是 `鍾`，输出是 `锺`**。

这说明引擎**确实动手了**，只是转错了：它把 `鍾` 转成了罕见异体字 `锺`，
而正确的简体是 `钟`。

我的补丁表映射的是 `鍾 → 钟`。但补丁在引擎**之后**运行，此时 `鍾` 已经不存在了
（被换成了 `锺`），所以 `translate()` 找不到要替换的字符，什么也没做。

**引擎的失败有两种模式，我只考虑了第一种：**

| 模式 | 表现 | 只映射源字的补丁能修吗 |
| --- | --- | --- |
| 一、原样不动 | `爲 → 爲` | ✅ 能 |
| 二、**转成错的变体** | `鍾 → 锺` | ❌ **不能**——源字已经没了 |

### 修法

补丁表拆成两张，第二张针对**引擎的输出**再映射一次：

```python
SIMPLIFY_PATCH_UNCHANGED = {"爲": "为", "於": "于", ...}        # 修"不动"
SIMPLIFY_PATCH_WRONG_VARIANT = {"锺": "钟", "麽": "么"}          # 修"动了但动错"
```

### 教训

**在你以为自己已经想清楚的地方，测试仍然可能证明你想漏了。**

这个 bug 的隐蔽性在于：如果我没写"每个补丁条目都要生效"这条测试，
它会一直潜伏着——因为它只在**特定的输入**（`鍾`、`麼`）上暴露，
而这两本书恰好用得不多。表面上一切正常，只有细看才会发现那 48 处没转对。

补丁表本身看起来也"对"：`鍾 → 钟` 语义上完全正确。**错的是时机**——它运行得太晚了。

## 共同模式

四个案例拆开看是四个 bug，合起来看是同一个模式：

| 案例 | 表面 | 实际 |
| --- | --- | --- |
| 下载器 | 下载成功 | 少了 75% 的内容 |
| 繁简 API | 98% 准确 | 4,800 处静默漏转 |
| 分段 | 标题全对 | 整章塌成一段 |
| 补丁表 | 语义正确 | 运行时源字已消失 |

四者都是"**操作成功，结果错误**"。共同点是：**没有任何一层告诉我出问题了。**

### 三条可操作的应对

**1. 给输出定可量化的健康指标，然后盯住它们。**

段落密度（100–400 字/段）这个指标帮我发现了案例三。下载字节数对比帮我发现了案例一。
指标不需要复杂，但必须**能被机器检查**——肉眼看不出一本书少了四分之一。

**2. 找到独立的见证，交叉验证。**

`Content-Length` 是服务端对同一件事的独立描述。用它比对本地结果，才能发现截断。
自己验证自己是没有意义的。

**3. 别信覆盖率，去问"剩下的部分是什么"。**

98% 听起来很好。剩下 2% 具体是哪些字、漏了会怎样——这个问题比那个数字重要得多。

## 方法论：为什么语料回归比单元测试重要

我后来把这个脚本重构成了库。重构最大的风险不是"新代码有 bug"，
而是**"我把原来对的东西改坏了"**——而单元测试**测不到这个**，
因为单元测试只覆盖我想到要写的那几条。

所以我做了一件事：把重构后的库拿去跑**九本真实的书**，
和已验证的旧流程逐项对比标题数、条目数、段落密度：

```
OK  喻世明言     indent  h1  40 h2  40       144 字/段     356,243 字
OK  警世通言     indent  h1  40 h2  40       151 字/段     373,837 字
OK  醒世恒言     indent  h1  40 h2  40       164 字/段     534,705 字
OK  初刻拍案惊奇  indent  h1  40 h2  40       165 字/段     394,071 字
OK  二刻拍案惊奇  indent  h1  39 h2  41       187 字/段     413,520 字
OK  今古奇观     indent  h1  80 h2  80       117 字/段     921,525 字
OK  世说新语     blank   h1  36 h2   3 en 1129   68 字/段    78,039 字
OK  聊斋志异     blank   h1  12 h2 496       267 字/段     476,618 字
OK  三怪客泛舟记  blank   h1   0 h2  19       250 字/段     356,836 字

mismatches: 0
```

**两者是互补的，不是替代关系：**

- **单元测试**证明"我测的这几条是对的"——它定义行为边界、防回归，是**规格**
- **语料回归**证明"我没有把原来对的东西改坏"——它覆盖我没预料到的路径，是**保险**

只写单元测试，你会很自信地发布一个改坏了的重构。

## 附：这个项目里其它"不会报错"的坑

有些没那么严重，但同样静默，一并记下：

- **同一个档案库里两种页面用不同的 CSS 类**。按一种写正则去解析另一种，返回**零结果**——不报错，就是空列表。
- **控制台会把中文压成乱码**。这是显示问题，数据是好的，但足以让人把好的解析器误判成坏的。
- **同一个书名对应两个质量不同的转写**。二刻拍案惊奇有 `24162`（28 卷）和 `26729`（39 卷）两个条目，标准版是 40 卷。随便取一个就得到一本残缺的书。
- **主题不能从操作系统推断**。阅读页跟 `prefers-color-scheme`（系统），宿主程序有自己的设置。系统浅色 + 宿主深色的组合下，页面会在深色面板里渲染成白色。
